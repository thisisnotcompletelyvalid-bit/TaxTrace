# Allocation engine — implemented Phase 4 contract

Status: **implemented** in TaxTrace 0.2.0 / methodology 1.1.0.

## Inputs

- `FederalTaxResult` generated by the versioned tax engine;
- active `RevenuePoolMapping` rows for the tax year;
- active `PoolSpendRule` rows for the spending fiscal year;
- actual OMB `SpendFact` rows in the `omb_account_outlay` scope;
- source-snapshot provenance.

## Pipeline

1. Convert supported tax result fields into `RevenueType` amounts.
2. Route each revenue amount to one or more `FundingPool` records using effective-dated mapping shares.
3. Select only OMB actual-outlay facts eligible under the pool's active spending rule.
4. Compute pool weight `E_j / sum(E)` for each eligible fact.
5. Attribute the user's pool contribution to those facts.
6. Reconcile cent rounding so child allocations sum exactly to the pool contribution.
7. Aggregate fact allocations into the selected additive receipt partition.
8. Preserve missing-detail pool contributions as `UNALLOCATED_DETAIL`, never as invented program detail.

For fungible general revenue:

`A_j = C_general × E_j / ΣE_general_eligible`

For dedicated revenue the same proportional operation occurs **after** the revenue has first been restricted to its legally/accountingly relevant financing pool.

## Current federal pool-spend rules

- `FED_GENERAL`: OMB actual account outlays except the Social Security 650/651 base; Medicare remains eligible because it is materially mixed-funded; relation `ALLOCATED`, confidence B.
- `OASI`: Social Security 650/651 spending base; relation `DIRECT`, confidence D because the current public spending grain does not separate final OASI uses from DI.
- `DI`: Social Security 650/651 spending base; relation `DIRECT`, confidence D because the current public spending grain does not separate final DI uses from OASI.
- `MEDICARE_HI`: Medicare 570/571 spending base; relation `DIRECT`, confidence D because the broad Medicare spending classification also contains expenditures financed from other sources.

If one purpose receives attribution from multiple pools, its combined display status is `MIXED_FUNDING`; the individual provenance entries retain the underlying `DIRECT` or `ALLOCATED` relationship.

These rules are rows in the database rather than hidden UI logic.

## Conservation invariants

For every mapped revenue type:

`sum(pool allocations) == tax amount`

For every funding pool:

`sum(receipt children) == user contribution to pool`

For every complete top-level receipt:

`sum(purpose nodes, including explicit residuals) == total allocable supported taxes`

Explorer views separately enforce:

`sum(view nodes, including residual) == selected parent scope amount`

## Provenance

Each receipt node contains:

- tax year and spending year at the receipt level;
- relation label and confidence grade;
- formula description;
- financing-pool code/name;
- active pool-spend rule explanation;
- actual metric/status;
- source snapshot IDs/names/URLs/reference periods/parser versions.

## Non-additive dimensions

Purpose, agency, account, program activity, object class, and award views can describe overlapping spending. Values may be summed **within one response explicitly marked additive**, but values from different views must not be summed together.
